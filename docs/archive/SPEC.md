## 1. Контекст и цель
Local-first, mobile-first PWA для **нескольких личных пользователей** (автор, жена, др. — без аккаунтов/сервера) для подготовки к **A1 PLA**. **Модель мульти-юзера:** каждый пользователь — на **своём устройстве/установке/браузер-профиле**; в пределах одной установки прогресс единый и НЕ разделяется по профилям (нет аккаунтов/сервера/синка — §16). Раздельный анализ обеспечивается тем, что выгрузка телеметрии помечена локальным `userAlias` (§13.2). Должна: (1) покрывать формат экзамена (`teacher_matriz.md`); (2) исправить провалы прошлой итерации — **лексика, род→артикль, предлоги** (числа/спряжение там работали); (3) работать **офлайн**; (4) давать **полную выгрузку телеметрии обучения** для анализа эффективности (§13).

### 1.1 Главные методические выводы (из опыта пользователя)
1. **Производство > узнавание.** Числа зашли, потому что требовался **ручной ввод**. Выбор из вариантов сам по себе слабо учит.
2. **Угадывание убивает обучение.** В переводном MC длина/структура фразы «протекает» ответ (три слова в оригинале → ищешь вариант из трёх слов) — отвечаешь не зная. → дистракторы обязаны быть **паритетными** (§6.3), а воспроизведение — приоритетным (§4.4).
3. **Предлоги: не с чего начать.** Много контекстных исключений (`ir a casa` — свой дом/коротко vs `ir para casa` — дом как пункт/насовсем). Без справочного материала и пологой кривой — стена. → **справочный слой (§4.9)** + **градуированная сложность (§4.8)** + контекст-явные задачи (§4.3).

**Принцип №1:** каждый навык — генеративный структурированный дрилл с объективной проверкой и приоритетом производства; перевод-MC вторичен и только с паритетными дистракторами.

### 1.2 Перенос рабочих режимов v1 (ОБЯЗАТЕЛЬНОЕ требование)
Удачные функции первой версии (`~/dev/personal/lingvago`) **переносятся в новую версию** — это **NumbersMode (числа)** и **ConjugationMode (спряжение глаголов)**. Они доказанно работали, и причина успеха совпадает с Принципом №1 → **сохранить именно ту механику, не «переизобретать» в узнавание:**
- **NumbersMode** — генеративный, без зубрёжки фиксированных карточек: случайное число → **ручной ввод** в обе стороны (цифра → пропись PT и пропись PT → цифра); сборка по правилам (vinte e três, cento e quarenta e cinco); бесконечная вариативность; объективная проверка строкой. Диапазон расширяемый (0–100 → 1000+), включая **порядковые** (cardinais+ordinais — требование Grupo III матрицы).
- **ConjugationMode** — паттерн «меняй окончание»: дано лицо+инфинитив → **ввести форму**; плюс «собрать таблицу»; приоритет производства над выбором. **Улучшение естественности (см. §5а):** генерировать НЕ случайным слот-филлом (даёт бессмысленные фразы), а из **аутентичных предложений корпуса** + банка коллокаций → осмысленно, естественно и в формате экзамена.
- **Полнота охвата (ОБЯЗАТЕЛЬНО):** ConjugationMode покрывает **ВЕСЬ инвентарь глаголов экзамена** — `extraction/normalized/verbs_inventory.json` (**126 глаголов** из ВСЕХ материалов: livro, caderno, notebook, листы преподавателя; правильные **и** неправильные). 43 имеют готовые таблицы спряжения; правильные достраиваются по правилу; каверзные/со-сдвигом-основы без таблицы помечены `needsTableReview` (acontecer, agradecer, conhecer, oferecer, sentir-se, valer, vestir, haver, …) — для них нужна **верифицированная таблица до показа в экзамен-режиме** (контент-QA §6.5).
- Оба режима — класс **deterministic/seeded** генераторов (§6.1), питают mastery; не геймифицируются. Перенести их рано (они уже доказали ценность), не понижая в MC-узнавание.
- **Подтверждение паритета — гейт замены v1:** оба перенесённых режима должны быть подтверждены рабочими в v2 до вывода v1 из эксплуатации (cutover — §10.6).

## 4. Педагогическая методика

### 4.1 Два движка
**FSRS** — факты (значение слова×2 направления; **род слова**; «опасные» неправильные формы). **Генеративные дриллы + mastery** — процедуры (артикль, предлог, спряжение, согласование, числа).

### 4.2 Граф навыков (зависимости → фидбек и подбор сессии)
```
род ─► артикль(def/indef) ─► множ.число ─► согласование прил. ─► контракции(de/em/a+арт.)
                                                        ▲
предлог(origem/local/tempo/movim./lugar) ──────────────┘ (зависит от рода/артикля)
ser/estar ─► выбор по контексту;  основа глагола ─► окончание(1/2/3) ─► неправильные
```
Ошибка в зависимом → фидбек указывает на родителя (ошибся в `na` → «Grécia fem → a → em+a=na»).

### 4.3 Предлоги — под-навыки + контекст-исключения + кривая
Под-навыки (раздельный mastery): origem-страны · localização-страны · tempo · movimento (`a` vs `para`; chegar **a**/sair **de**·**para**) · transporte · lugar-locuções · контракции с демонстративами.
**Контекст-исключения** (нельзя решить по слову — задача ДОЛЖНА давать контекст; класс «content-anchored», §6.1): напр. `ir a casa` (свой дом/коротко) vs `ir para casa` (дом как пункт назначения/насовсем); такие пары явно показываются с disambiguating-контекстом и объясняются в справочнике (§4.9). **Спорные** (опц. артикль Espanha/Itália/França) — принимать несколько верных ответов либо не включать в строгий MC до прохождения.

### 4.4 Производство вместо угадывания (ядро)
- **Прогрессия каналов:** прочитать правило (справочник) → разобрать пример → **узнавание (MC, паритетные дистракторы)** как скаффолд → **производство (печатный ввод/сборка)** как основная проверка → смешанный контекст.
- mastery различает «верно через производство» (сильное свидетельство) и «через узнавание» (слабее). «Уверенно» требует производства в разных контекстах.
- Для лексики: основной формат — ввести слово/форму или собрать `артикль+существительное`/cloze; переводной MC — лишь ранний скаффолд и только с §6.3.

### 4.5 Интерливинг
Смешанная сессия по умолчанию: **60% слабые · 25% интерлив старого · 15% экзамен-формат**. Доступны узкие дриллы и mock.

### 4.6 Mastery (богатый)
На под-навык: точность, recency, streak, среднее время, **тип ошибки**, **доля производства**. «Уверенно» = успех в РАЗНЫХ контекстах + устойчивость во времени + достаточная доля производства (не «N из 12» в одном шаблоне).

### 4.7 Разбор ошибок
Неверно → правильный ответ + мини-правило (deep-link в справочник §4.9) + «добавить связанные карточки в повторение» + (опц.) пометить итен комментарием (→ телеметрия §13).

### 4.8 Кривая сложности (градуированные уровни)
Каждый навык разбит на уровни L1→Ln: от самого регулярного к исключениям; уровень не открывается, пока предыдущий не освоен. Пример (предлоги):
`L1` origem стран с явным артиклем (do Brasil/da Rússia) → `L2` localização (no/na) → `L3` артикль-ноль (Portugal/Marrocos) → `L4` tempo (à tarde/de manhã/em maio/no verão) → `L5` movimento a/para → `L6` контекст-исключения (a casa/para casa) → `L7` смешанное/экзамен-формат. Скаффолдинг на каждом уровне: правило → пример → узнавание → производство → интерлив. Это и есть «пологий вход», которого не хватало.
**Требование:** КАЖДЫЙ навык фазы 1 поставляется минимум с уровнями **L1–L3** (простое → базовые случаи → первая комбинаторика); провальные навыки (предлоги, род/артикль, ser/estar) — с полной лестницей. Уровни навыка декларируются в его модуле (число и критерии перехода), чтобы не было «изобретённых на месте» разных гейтов.

### 4.9 Справочный (дидактический) слой — перечитываемый
Первоклассный раздел **«Справочник»**: краткие, легко-усваиваемые материалы по темам, доступные **из любого места** (дашборд, дрилл, фидбек ошибки). Особенно предлоги: шпаргалки с правилами, **деревья решений** («как выбрать de/em/a»), таблицы, **контекстные исключения с примерами** (a casa/para casa и т.п.), worked-examples. Источник: `grammar_full` + `prepositions_teacher` + рабочие листы преподавателя. Не геймифицировано; цель — возвращаться и перечитывать. Каждое правило адресуемо (`ruleRef`) для deep-link из ошибок.
Схема `referenceCard`: `{ id, topic, subskill, level, title, body(md), examples[], decisionTree?(узлы вопрос→ветка→правило), relatedDrills[], ruleRef[], sourceRef }`.

### 5а. Осмысленная генерация (против бессмысленных фраз) — для глаголов и всех процедурных дриллов
Свободный случайный слот-фил («любое лицо + любой глагол + любой объект») даёт грамматически верные, но **семантически странные** фразы («Eu ponho a mãe») — теряется смысл, употребление и сходство с реальной речью/экзаменом. Поэтому генерация — **по приоритету источника**:
1. **Сиды из аутентичного корпуса** (главный источник): реальные A1-предложения из `extraction/verbatim` (упражнения «Completar com o verbo (X)», диалоги, тексты; `teacher_verbosinfo` — примеры на глагол) → «выколоть» целевую форму, пользователь вводит. Гарантированно осмысленно и **в формате экзамена** (Grupo III: «completar o texto com os verbos»).
2. **Банк коллокаций при глаголе** (естественные дополнения/конструкции из учебника): tomar→café/banho/o pequeno-almoço; fazer→anos/desporto; ir→**ao** cinema/**à** praia; gostar→**de**… → фразы остаются сенсибельными, **попутно учатся коллокации и предлоги**.
3. **Курируемые шаблоны на глагол** (фиксированный осмысленный контекст, варьируется лицо/глагол).
4. **Кривая к связному cloze:** L1 — один глагол в фиксированной фразе; L2 — лицо/шаблон варьируются; **L3 — короткий связный текст/диалог с несколькими пропусками** (как «Completar o texto» в caderno) — осмысленнее и ближе к реальному заданию.

Trade-off: чуть меньше «бесконечности» (банк конечен), но вариативность велика (сиды × лица × глаголы), а качество и польза несравнимо выше. Можно оставить узкий «raw-режим» чисто на окончания. Это классы **seeded-parametric / content-anchored** (§6.1) под контент-QA (§6.5). Применимо ко всем дриллам, где есть риск бессмысленных фраз.

## 6. Генераторы: таксономия и гейты

### 6.1 Классы (только надёжные питают mastery/метрики)
1. **Deterministic** (ответ из правила) · 2. **Seeded-parametric** (верифиц. семя + подстановка) · 3. **Content-anchored** (привязан к тексту/аудио/контексту с верифиц. ключом — сюда и контекст-исключения предлогов) · 4. **Non-auto-assessable** (письмо; picture без ключа — НЕ питают авто-метрики). «Бесконечность» — только классы 1–2.

### 6.2 Гейт задачи (обязательные поля Task)
`prompt`·`answer`·`acceptedAlternatives[]`·`distractors[]` (**обязателен только при `channel=recognition`/MC; при `channel=production` — опускается/пуст**)·`skill`/`subskill`·`level`·`channel`(recognition/production)·`sourceRef`·`ruleRef`·`ambiguityFlag`. Контент-QA (§6.5) проверяет обязательность полей **по каналу** (distractors требуются лишь для recognition). Без верифиц. ключа — не показывать в экзамен-режимах.

### 6.3 Дистракторы — паритет (анти-протечка; прямое требование пользователя)
Все варианты ДОЛЖНЫ совпадать по: **длине/числу слов**, синтаксической структуре, регистру/части речи, грамматической форме — чтобы форма/длина не выдавала ответ. Для фраз — все опции фразы сопоставимой длины и конструкции. Плюс: один грам-класс, **правдоподобные «конкурентные» дистракторы** — строятся из ТИПИЧНЫХ ошибок изучающих (для рода — противоположный артикль; для предлога — соседняя контракция da/de/na/no), чтобы заставить припоминать; неправдоподобный/очевидно-неверный дистрактор не учит ничему (Little & Bjork, см. `LEARNING_SCIENCE.md §3`). **Без дублей-верных**, без ловушек на опц.-ответах, каждый дистрактор — с объяснением. Если правдоподобный паритетный набор не собрать → задача переключается на **производство** (ввод), а не MC.

### 6.4 Picture-задачи / answer-key gaps
Picture-inferred и всё помеченное в `human_review_queue.md` как «inferred без ключа» — исключены по умолчанию (нужны asset-id + ключ + дистракторы + sourceRef).

### 6.5 Контент-QA
Неверный ключ опаснее отсутствия фичи. CI-скрипт: каждый итен/семя имеет полный набор полей §6.2; прогон PT-линт/Codex-проверки банка семян (переиспользуем `extraction/verification`).

## 9. Экзамен-режим и метрики
### 9.1 PaperSimulation: таймер 90 мин, **без подсказок, без мгновенного фидбека**, ответы фиксируются, разбор в конце; опц. экспорт в печать. (Практика на дашборде — отдельный режим с мгновенным фидбеком.)
### 9.2 Scoring-карта (детерминированная): G I=20; II=5(V/F)+4(restrita)+4(intruso); III=25; IV=рубрика. **Перевод в баллы группы (из 50):** per-item = 50 / N_итенов (G I: 50/20 = 2.5/итен; G II: 50/13; G III: 50/25 = 2/итен); G IV — рубрика по шкале 0–50. Именно эти **0–50 баллы группы** идут в §9.3 (`recent_mock_g` = баллы_группы / 50) и в mock-таблицу MVP_PLAN WP-A — так счёт итенов и 50-балльные группы согласованы. **Resposta restrita (4 итена):** авто-проверка по нормализованному сравнению (регистр/пробелы/диакритика-толерантно) против списка **accepted-answers** + ручная до-оценка спорных в review-UI; помечается «частично авто». **Письмо** — «не авто-оценено», рубрика+сохранение для ручной проверки.
### 9.3 Готовность: `readiness = Σ_group weight_g × min(coverage_g, recent_mock_g)` (результат 0..1). Определения термов:
- **weight_g** — вес группы; группы равны (4 × 50 баллов), нормируются в сумму 1 → каждая `0.25` (если какая-то группа исключена, см. ниже, веса оставшихся пере-нормируются в сумму 1).
- **coverage_g** ∈ [0,1] — доля экзамен-эквивалентных под-навыков группы, выведенных в «уверенно» (mastery §4.6), взвешенная по их доле в группе.
- **recent_mock_g** ∈ [0,1] — последний валидный mock-счёт группы / её максимум (напр. Grupo III: баллы/50). «Recent» = **последний mock не старше 7 дней**; старее — считается отсутствующим.
- **Нет валидного mock у группы ИЛИ группа — заглушка** (нет рабочего дрилла с верифиц. ключом): группа **исключается из суммы** (не обнуляет readiness), на дашборде — статус **«не экзамен-эквивалентно»** (не ложный %), и в подсказке «нет данных mock». Готовность считается только по группам с данными; число учтённых групп показывается рядом, чтобы % не вводил в заблуждение.
- **Если включённых групп НОЛЬ** (нигде нет валидного mock/рабочих дриллов): readiness = **«не определена»** (НЕ 0% и НЕ 100%); дашборд показывает «нет данных для оценки» и призыв сделать первый mock. Любой частичный % всегда сопровождается числом учтённых групп.

### 10.5 E2E-тесты (требование ПЕРВОЙ реализации)
E2E-покрытие закладывается с **первой же app-сборки** (WP-A/WP-B), не откладывается «на потом». Инструмент — **Playwright** (Chromium, headless-CI; ставится как devDependency, без глобальных бинарей — `pnpm exec playwright`/`npx`). Тесты гоняют **собранный PWA** (`vite preview` или статический сервер `dist/`), а не dev-режим — чтобы реально проверять офлайн/SW-путь, а не голый Vite-HMR.
- **Обязательный E2E-минимум для WP-A/WP-B (гейт Фазы 1):** (E1) **первый запуск** — app-shell грузится, survival-kit-страница (WP-A) отрисована; (E2) **тема** — Светлая/Тёмная ставят `data-theme="light"`/`"dark"`, **Авто снимает `data-theme`** (следует `prefers-color-scheme`); выбор переживает перезагрузку (localStorage); (E3) **локализация** — переключатель RU/EN меняет язык UI, системный дефолт + fallback EN отрабатывают, выбор сохраняется; (E4) **офлайн** — после первой загрузки повторный визит при `context.setOffline(true)` отдаёт app-shell и survival-kit (SW); (E5) **справочник (WP-B)** — открывается ≥1 `referenceCard` офлайн; (E6) **обновление SW** — новый билд вытесняет старый app-shell без потери прогресса (Workbox `skipWaiting`+`clientsClaim`) — это обязательный тест §10.2 #3, покрытый в E2E-гейте.
- **Условные E2E (добавляются вместе с WP, как unit-тесты §10.2):** production-ввод с верифиц. ключом и фидбэком→справочник (WP-C); таймированный mock со счётом по группам (WP-D); export → import/restore round-trip (WP-E).
- Тесты живут в `e2e/`, запуск `pnpm e2e`; CI-агрегат `pnpm check` = typecheck + lint + unit + build + **e2e** (**build перед e2e** — E2E гоняются по собранному `dist/`). Привязка к фактически построенным WP — как у unit (§10.2): сборка без условной WP не валит гейт из-за её E2E.
### 10.6 Замена v1 (cutover на ту же установку) — ОБЯЗАТЕЛЬНОЕ требование
Цель: lingvago2 **заменяет работающую v1** (`~/dev/personal/lingvago`) на том же устройстве/установке, **не теряя установленный PWA-ярлык и не разрушая данные v1**. Замена выполняется **не раньше** DoD Фазы 1 и **только после полного гейта замены** ниже (DoD Фазы 1 + подтверждённые NumbersMode/ConjugationMode в v2 + зелёные E2E E1–E6 + ручная офлайн-проверка на телефоне — см. «Порядок вывода v1»); один DoD Фазы 1 сам по себе недостаточен.
- **PWA-идентичность:** v2 деплоится на **тот же origin и `scope`/`start_url` = `/`**, что v1 → установленный PWA авто-обновляется на месте (`registerType:'autoUpdate'`), иконка на домашнем экране сохраняется. Manifest `name`/иконки/`theme_color`/`background_color` обновляются под Calm (DESIGN_TOKENS), но `scope`/`start_url` **не меняются**. Новый SW корректно вытесняет старый (Workbox `skipWaiting`+`clientsClaim`) — без «застрявшего» старого app-shell. (Хостинг/URL подтвердить перед cutover — это предусловие замены.)
- **Изоляция БД (не разрушать v1):** v2 использует **отдельное имя IndexedDB `lingvago2`**, не трогая v1-базу **`lingvago`** (`decks·words·cardStates·grammarCardStates·sessions·settings`, Dexie v3). Базы сосуществуют на одном origin → откат на v1 возможен до окончательного вывода.
- **Прогресс v1 НЕ авто-мигрируется:** контент-модель и граф навыков v2 другие (§7) → **чистый старт прогресса** в v2; v1-данные остаются нетронуты (архив/откат). Опциональный one-time импорт v1-FSRS — **вне Фазы 1** (backlog), только как явное действие пользователя, без авто-затирания v1.
- **Порядок вывода v1:** v1 выводится из эксплуатации **только после** того, как v2 достигла DoD Фазы 1 (MVP_PLAN §6) и перенесённые режимы (NumbersMode/ConjugationMode, §1.2) подтверждены рабочими в v2. Гейт замены = зелёные E2E (E1–E6) + ручная офлайн-проверка на реальном телефоне.

## 13. Телеметрия, выгрузка и обратная связь (первоклассная фича)

**Цель:** как reflection*-скилы изучают работу агентов, так здесь — изучать **реальные сессии обучения**, чтобы находить неэффективные места и точки роста, и улучшать и технику, и методику. Без бэкенда → **ручная выгрузка** архива, который пользователь шлёт файлом.

### 13.1 Что логируется (достаточно для анализа эффективности)
- **На попытку (`attempts`):** sessionId, ts, modeId, skill/subskill, **level**, generator-class, **channel**(recognition/production), taskId+sourceRef+ruleRef, prompt, показанные опции (для MC), ответ пользователя, правильный ответ, верно/нет, **время ответа**, число правок/возвратов (для ввода), **тип ошибки** (категория), FSRS до/после, mastery до/после, ambiguityFlag.
- **На сессию (`sessions`):** рецепт, длительность, состав по навыкам, точность, динамика точности (утомление), доля производства vs узнавания.
- **Производные сигналы (считаются при экспорте или анализе):** **guess-rate** (быстрый верный на ранее-невиданном итене = вероятная догадка — прямо ловит «протечку длины фразы»), кривые обучения по навыку, item difficulty/discrimination (какие итены слишком лёгкие/двусмысленные), drop-off, retention.

### 13.2 Аннотации пользователя
Кнопка «пометить» на любом итене/сессии → свободный комментарий («тут можно угадать по длине», «правило предлога неясно»), сохраняется в `annotations` и попадает в выгрузку. Мульти-юзер: каждый экспорт помечен локальным `userAlias` (без аккаунтов/PII).

### 13.3 Выгрузка
Одна кнопка → **архив** (JSON-бандл: attempts+sessions+**cardStates (FSRS: состояние карточек + before/after-снимки)**+mastery+annotations+settings + schemaVersion+appVersion+contentVersion; опц. zip). Этого набора достаточно для **restore** (§10.2 #5): cardStates восстанавливаются напрямую; mastery — из cardStates+attempts. Шеринг — **нативные механизмы телефона**: Web Share API (`navigator.share` с файлом) → download-fallback. **Импорт в MVP — только restore (восстановление своего состояния на устройстве);** слияние нескольких бандлов (merge разных пользователей) — вне MVP, делается внешним аналитическим инструментом (§13.4).

### 13.4 Аналитический воркфлоу (оффлайн, reflection-style)
Формат бандла — **analysis-ready** (плоские записи, стабильные id, схема версионирована), чтобы внешний инструмент (будущий Claude-скил `reflect-learning`, по аналогии с `reflect-stats`/`reflect-memory`) мог из нескольких бандлов (автор/жена/др.) находить: неэффективные итены (высокий guess-rate, низкий retention), навыки с плоской кривой, частые типы ошибок, точки отвала, и предлагать правки и контента, и методики. Это замыкает цикл «учусь → выгружаю → анализирую → улучшаю приложение».

### 13.5 Приватность
Всё локально; выгрузка — явное действие пользователя; в архиве — только учебные данные и то, что пользователь сам написал.
